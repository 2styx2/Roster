# Design decisions log (2026-10-29)

These came from a grilling session in which each question was asked with a recommended answer. The lasting, hard-to-reverse ones are also ADRs.

| # | Question | Decision |
|---|---|---|
| — | Is this worth building? | Yes as a team or personal tool. XPipe is the closest rival. The value is roster's model (team Inventory in git, per-service Logins, review gate, secrets kept from the UI), not "another SSH client". See [vision.md](vision.md). |
| Q1 | Who is it for? | The team eventually. It starts as a personal project and may be open-sourced or sold later. |
| Q2 | Platform | Cross-platform, anywhere with a display (Windows, X11, Wayland, WSLg). **Tauri.** |
| Q3 | v1 scope | Host finding, terminal tabs with automatic login, Host details, opening web services. |
| Q4 | Inventory writes | **Yes**, the app writes to the Inventory (it was read-only at first, then changed). |
| Q5 | Secrets | Never shown in the GUI. The app must really unlock the vault (Bitwarden or whatever provider the Inventory uses). |
| Q6 | Terms | **Host** is the saved entry. **Session** is one live terminal connection. |
| Q7 | Repo | A separate repo, **local only** while experimenting. *Superseded by Q56: the app now lives in the roster repo's `app/`.* |
| Q8 | "Native" | Native window chrome, shortcuts, fonts and light/dark. Our own design inside. SecureCRT is a skeleton, not a style guide. |
| Q9 | Frontend | React + Vite + **TypeScript (required)** + xterm.js (WebGL). Get it right on Windows first, then the Linux VM. |
| Q10 | API | `roster serve`, JSON-RPC over stdio, returning roster's **existing objects** (roster ADR 0001). |
| Q11 | Session transport | System `ssh` in a PTY, with passwords through SSH_ASKPASS (roster ADR 0002). |
| Q12 | App lock | Unlocking the vault is the app lock. Locks after 15 minutes idle (configurable). |
| Q13 | Write flow | Edit through roster, keeping comments, then diff, then **Publish** (commit and push to infra `main`, pulling first). *Ticket 12: Publish commits `roster.yml` alone (never `folders.yml` or any other file; other uncommitted files refuse it) with the infra repo's own git identity, and pushes to the branch's upstream, never forced. "Pulling first" is a fetch, then a fast-forward only over upstream commits that leave `roster.yml` alone; if `roster.yml` moved there, or the push is rejected, it stops with the Pending changes kept. `roster sync` runs after.* |
| Q14 | Backends | All three: native Windows, the Windows app with roster in WSL, and Linux. Auto-detected per machine. |
| Q15 | Name and location | `roster-desk` in `~/work/roster-desk`. *Superseded by Q56: it's now the roster app, in `app/` of the roster repo.* |
| — | Keyboard | Vim keys, mostly keyboard, mouse fully supported. |
| Q16 | Backend setting | Local or WSL: <distro>. The Windows default is auto-detected, and the Config can override it (`backend =`). Originally a Settings screen option, then replaced by Q24. |
| Q17 | Layout | Terminal first: the Picker overlay is the main way to find Hosts, side panels are closed by default, and there's one thin tab strip. |
| Q18 | Leader | Ctrl+Space, configurable. |
| Q19 | Vim scope | Vim keys in the app everywhere except the terminal. Can be turned off. Form fields stay ordinary inputs. |
| Q20 | Quick Connect | "Save to vault" saves only after the login succeeds. It creates the Vault item `<host> ssh` and the Host (reviewed, not enrolled) as a Pending change. The same checkbox appears for `auth: prompt` Hosts. |
| Q21 | Vault writes | Bitwarden only. Other providers come later, when needed. |
| Q23 | Config language | **Lua**: `init.lua` in the user config dir, run with mlua (Lua 5.4 built in). See [ADR 0004](../adr/0004-lua-config-file-only.md). |
| Q24 | Settings screen | **None. The config file is the only place to change settings**, as in WezTerm and Neovim. Remembered things like window size and recent Hosts are State, not Config. |
| Q25 | When | **Iteration 2**, with the design pass (ticket 21). In iteration 1 the keymap and options are built as data tables with defaults, ready for the Config to override. |
| Q26 | Window chrome | **A custom title bar like Slack's** (frameless window; our own bar with app icon, tabs, the Picker search, and minimize, maximize and close). It replaces Q8's "native title bar". The rest of Q8 stays: platform shortcuts, system font and OS light/dark. It lands in iteration 2's design pass (ticket 09). |
| Q27 | Visual direction | **Linear is the main reference**: lean, dense and quiet, with a muted palette and one accent, thin 1px borders, small type, fast and subtle motion, and keyboard-first with a command palette. Tabby and Warp are secondary references. |
| Q28 | Logo | Five concepts are prototyped on branch `prototype/logos` (`npm run proto:logos`). The user picks one or more to refine. |
| Q29 | Logo + accent | **D1 "Network R"** (seven nodes joined into an R, with the accent node at the end of the leg) and **jade `#1f9d68`** as the default accent. Prototype: branch `prototype/logos`. *Superseded by Q57: the logo is Gap orbit (plain) and the accent Apricot flare.* |
| Q30 | Fonts | **Inter** (Linear's UI font) for the UI. **Iosevka** for the terminal and the wordmark. Both are defaults the Config can change. |
| Q31 | Active item | The **raised** style: a slightly lighter fill plus a 1px outline. No underlines. |
| Q32 | Layout | **Title bar 3, extended:** the bar holds only the mark and minimize, maximize and close. **Sessions, personal Folders and the Inventory tree live in a left sidebar**, like SecureCRT's Session Manager or an editor's file tree, in place of a tab strip. The status bar can be hidden. A **Key bindings panel** (`␣ ?`) lists the resolved keymap and where each binding comes from. Prototype: `prototype-shell.html` (A tree / B explorer). This replaces Q17's tab strip, Q26's tabs in the bar, and "side panels closed by default". The Picker stays on `␣ f`. |
| Q33 | Modularity | **Everything above is only a default.** The Config (`init.lua`) can change every color token (themes are sets of tokens; several ship), the fonts, the keymap, and the layout pieces: sidebar on/off and side, Sessions as a sidebar or as tabs, status bar on/off, what the title bar shows. The app behaves like an editor you configure. |
| Q34 | Folders | **Personal:** kept in this Box's State (drag, or `␣ a`) and definable in `init.lua`. They're never written to `roster.yml`. Teammates see only the Inventory's groups. |
| Q35 | When | The **sidebar is built in iteration 1**: ticket 07 builds Sessions in the sidebar instead of a tab strip, and ticket 17 (Inventory tree and Folders) moves to iteration 1. Colors, fonts, the title bar and polish stay in iteration 2 (09). Themes and layout options land in 21. |
| Q36 | View modes | **Two modes** (simplified from three on 2026-10-29, so both can be done really well), toggled with `␣ m` or F11. `init.lua` picks the starting one.
1. **Standard**, the everyday layout: Sidebar tree A, title bar, optional status bar.
2. **Focus**: true OS fullscreen with no chrome at all. You get around like in Neovim: `␣ b` fuzzy-finds open Sessions (Telescope's buffer list), `␣ f` fuzzy-finds Hosts, and `␣ ]` / `␣ [` cycle Sessions.

**Every mode keeps all of roster:** the Picker, `:` command line, Quick Connect, Host details, the Key bindings panel, Lock, Inventory edits and Publish all work in every mode. Modes change how things are shown, never what you can do. What the Sidebar shows in Standard is reached through overlays and finders in Tmux and Focus. Prototype: `prototype-shell.html?mode=standard|focus`. Focus can optionally show the thin tmux-style session bar (`[box] 0:esxi-02* 1:…`): off by default, turned on with `focus.status_line = true` in `init.lua`. The Tmux mode, Compact rail and Mini window ideas were dropped. Split panes are still out of scope. |
| Q37 | Your terminal config wins | **The terminal never fights the user's own setup.** Remote `.bashrc`, prompt, `LS_COLORS`, vim colour schemes and truecolor themes must render exactly as they do in any good terminal. The app sets `TERM=xterm-256color` and `COLORTERM=truecolor`, injects nothing else (no PS1, no sourced files, no output rewriting), and passes every escape sequence through. The 16-colour ANSI palette defaults to a neutral, standard one rather than the app accent. Themes and `init.lua` can change it, and a theme can say "leave the ANSI palette alone". |
| Q38 | Plugins and packages | **Neovim-style extensibility:**
- **Plugins** are Lua, run in the same runtime as the Config. They add commands, keys, themes, Sidebar sections, finder sources, status segments and event hooks.
- **Packages** are Plugins from git repos, listed in `init.lua` and pinned in `roster.lock` (lazy.nvim-style).
- The built-in features use the same registries.
- Plugins never see secrets, and their Inventory writes only become Pending changes.
- No plugin HTML/JS in v1.

See [ADR 0006](../adr/0006-lua-plugins-and-packages.md). Tickets 23–24, iteration 7. |
| Q39 | Per-mode layout | **Each view mode has its own layout table** in `init.lua`: which pieces show, where they go, and in what order. The pieces are the title bar, Sidebar (and its sections), session bar, status bar and its segments, and finders. For example, Focus can show the session bar at the bottom, and Standard can hide the status bar. Plugins can add pieces and segments to any mode. The defaults are the two modes as prototyped. |
| Q40 | No built-in vault | **The roster app will never have its own secret store.** Secrets stay in the user's password manager. The roster CLI and app only hold Login *references*, and never learn or keep a password beyond one lookup. Building a vault would mean owning encryption, recovery, sync, sharing and breach liability, and it would turn the product into the thing (Termius's vault) we set out to differ from. |
| Q41 | Local-only option | People without a team password manager get **local providers** instead of a vault: **KeePassXC** (`keepassxc-cli`, a local `.kdbx` file) is added, next to the existing `pass`. Both can read Logins and, like Bitwarden in ticket 13, create Vault items for "Save to vault". Ticket 25. |
| Q42 | Syncing your setup | `init.lua`, `roster.lock`, themes and personal Folders are plain files that sync through **git (dotfiles)**, the way the Inventory does. There's no vendor cloud. A `:config sync` helper that pulls and pushes that repo is a later proposal, not planned yet. |
| Q43 | Verified adds only | **A Host with a Login enters the Inventory, and a password enters the vault, only after a test login just succeeded with exactly those credentials.** That means the address was reachable, the host key was confirmed, and the user and password (or key) were accepted. This applies to the add-Host form (ticket 11), Quick Connect "Save to vault" (15), filling in `auth: prompt` Hosts (16), and changing a Host's Login in an edit (10). The order is always: verify, then create the Vault item, then add the Pending change. If the second step fails, the first is undone, so a failure leaves neither a stray Vault item nor a Pending change. Hosts *without* a Login (from `discover`) still enter as `reviewed: false` through the review gate. |
| Q44 | Clean errors everywhere | Every way a connection can fail, including entries made by hand in `roster.yml` or the vault, ends in a clean error with the Host, plain words, where the problem lives, the fix, and the raw message under Details. The catalog is `docs/app/errors.md`. `roster check HOST` / `:check HOST` run the diagnostics. A changed host key is never accepted automatically. Ticket 26, iteration 1. |
| Q45 | Live, two-way Inventory | Adding, removing and renaming **Hosts and groups** happens right in the Sidebar: `+` on a group heading, a row menu, `␣` keys and drag between groups. Each change writes `roster.yml` (comments kept) as a Pending change that you Publish (Q13). **Edits to `roster.yml` made outside the app show up in the Sidebar within a second**: `roster serve` watches the file, reloads it, and notifies the app. A file that doesn't load keeps the last good Inventory on screen with a clean error naming the line. Adding a Host with a Login still requires a successful test login first (Q43). Removing a Host asks for confirmation and never touches the vault. Tickets 28 and 10–12. *Reloading became Neovim-style (Q58, owner 2026-10-30): outside edits apply on `:source`, or within a second with `auto_reload = true`.* |
| Q46 | Folders in a file | Folders move from the State file into **`folders.yml`** next to `init.lua`: plain data that both you and the app edit. The app writes it on every Folder change, and edits made outside the app show up live. The app never rewrites `init.lua`, because that file is code. Folders that `init.lua` defines are shown marked "from init.lua" and can only be changed there. This supersedes the storage part of Q34; Folders remain personal and never go into the Inventory. |
| Q47 | Worst-case UI | Every screen is stress-tested with worst-case data using the `break-ui` skill: long and unbreakable names, 500+ Hosts, empty states, unicode, huge counts and narrow windows. The fixes ship with the design pass. Ticket 27, iteration 2. |
| Q48 | First Release | **No Release until iteration 5 is done.** Iterations 1–5 build up on `dev`, each tested by hand before the next one starts. After iteration 5, `dev` → `main` is tagged `v0.1.0`. After iteration 7 (Platforms + Plugins), it's tagged `v0.2.0`. |
| Q49 | Terminal font weight | The terminal defaults to **Iosevka Medium (500)**, with bold at 700. It's configurable in `init.lua` (`terminal.weight`, `terminal.bold_weight`). The UI stays Inter 400/500/600. Delivered with ticket 21. |
| Q50 | Dark background | **Roster dark is a neutral near-black like Linear's, with no blue tint:** bg `#08090a`, chrome and Sidebar `#0f1011`, raised `#191a1b`, lines `#1c1d1f`. The terminal background matches the bg. | Q51 | Bundled themes | Besides Roster dark and light, ship complete **Gruvbox Dark, Nord, Catppuccin Mocha and Tokyo Night** themes from their official palettes, each with its own background, surfaces, accent and ANSI colors. Accent text is dark on jade in Roster dark; Roster light uses `#17845a` for contrast. *The Roster colours are superseded by Q57 (apricot accent with Ink text in dark, `#9b411a` with white in light); every bundled Theme also gets a second tone.* |
| Q52 | Sign-in with 2FA | The lock screen also handles **full sign-in**: server, email, master password, every two-step method the provider's CLI supports (for Bitwarden: authenticator, email, YubiKey OTP, new-device code, API key, SSO), and a clean message for the methods it can't do. | Q63 | Mesh: Host-to-Host access from one Box | **roster runs on one Box and sets up Host-to-Host access itself (owner, 2026-10-30): no roster, vault or password on any other machine, nothing to install or update there.** *Inventory:* a group's `mesh: true` lets its Hosts reach each other both ways; it cascades (`defaults` → group → Host), so `mesh: true` in `defaults` meshes every group, including new ones from `discover`; `mesh: false` opts out; unreviewed Hosts never join. Top-level `links:` add one-way reach across groups and networks, Host or group to Host or group (`{ from: subnet-1, to: subnet-42 }`, `both: true` for two-way). Each Host logs in to a peer as **that peer's** configured user. *How:* `roster mesh` (plan with `--dry-run`, then apply; `roster setup` runs it for meshed groups) makes a key **on** each source Host (the private key never leaves it), installs it on its peers tagged `roster-mesh:<host>` with `from="<source IP>"` and no agent or X11 forwarding, copies the peers' recorded host keys into the source's `known_hosts` (strict checking), and writes an ssh config so `ssh <peer>` works and a `ROSTER.md` listing only that Host's peers for Claude there (imported from `~/.claude/CLAUDE.md` when Claude is installed). It never runs on its own: after a Publish, `sync` and the app say "mesh out of date" with a one-key apply. Apply goes one connection at a time (rate limiters). *Edges:* Hosts that can't take a key (`enroll: false`, appliances) stay in the mesh as password peers: ssh asks the person for the password, roster never copies a password to a Host, and `ROSTER.md` tells Claude to ask the user to log in. ESXi works both ways, with the key and config kept somewhere that survives a reboot, and `roster check` notices if they're lost. Links across networks are tested from the source ("orion-2 can't reach …:22") rather than assumed; a `via:` hop is later. Removing a Host, a link or `mesh: true` removes exactly its tagged entries on the next apply; down Hosts are kept as "pending" and finished when they're back; `roster check` reports drift; `roster mesh --rotate HOST` replaces a key. **Cut:** `roster mesh cut HOST` (one key in the app) removes HOST's key from every peer at once, in parallel, and every peer from HOST, without waiting for a Publish; the Box's own access stays so you can investigate (`roster revoke` is separate); it writes `mesh: false` for HOST as a Pending change so the cut survives the next Publish; it is quick but complete: every peer is confirmed, and any peer that's down or not answering gets a loud warning ("cut pending on 2 Hosts") until it's done when they're back. *Many Boxes:* any Box can apply; the mesh is derived from `roster.yml` only and keys are tagged per Host, so applying twice changes nothing and says "already in the mesh". *Visible risk:* the app shows each Host's reach ("orion-2 can reach 7 Hosts") and draws Links on the map; mesh and links changes show in Publish's diff. *Not a VPN:* Tailscale and other VPNs make the network path (and need an agent on every machine); the mesh manages who may log in where over the network you already have, and the two combine. T39 (#71), iteration 6. A **Topology** view (T40, #73) draws the Box, Hosts by group, Mesh reach and Links. |
| Q60 | Unknown host keys in Sessions (issue #45) | **Ask once, in the app (owner, 2026-10-30).** A Session to a Host whose host key roster hasn't recorded no longer trusts it silently (`accept-new`). The app first shows the Host, its address, and the key's type and SHA256 fingerprint, in plain words ("roster hasn't seen this Host's key before"), and asks whether to trust it. Trusting it records the key in roster's known hosts and connects; declining connects nothing and records nothing. A key that differs from the recorded one is still refused, never asked about (Q44). Verified adds and edits already record the key (Q43; review fix for address changes), so the question only comes up for Hosts that reached `roster.yml` another way (hand edits, a teammate's Publish) before `roster setup`/`sync`. Rejected: keep `accept-new` (trusts the first key without telling you) and strict refusal until `setup`/`sync` (safe but blocks a new Host a teammate just added). The CLI's own `roster ssh` is unchanged. Ticket 36, iteration 4. |
