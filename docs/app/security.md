# Security model

The roster app keeps roster's promise: **secrets are fetched when needed, kept in memory, and never written, printed or shown.**

## Where a password goes

| Step | Holds the secret? |
|---|---|
| Vault (Bitwarden, …) | yes, at rest |
| `roster serve` process memory | yes, while unlocked |
| Private askpass socket (a user-only named pipe on Windows), one-time token | yes, in transit, once |
| Session process env (the token only, never the password) | the token, for the Session's life |
| `roster askpass` → `ssh` | yes, in transit |
| Rust core | **never** |
| Frontend, app State, Config, logs | **never** |
| Terminal output and scrollback | **never** (ssh reads the password itself) |

A few exceptions are typed by you and leave the UI straight away:
- **The master password:** sent once to `vault.unlock`, and the field clears. Bitwarden turns it into a session key and roster drops it. KeePassXC (ticket 25) has no session: `keepassxc-cli` opens the `.kdbx` again on every call, so `serve` keeps the master password itself in memory until `vault.lock` and gives it to each `keepassxc-cli` call on its stdin, never on a command line or in an error.
- **A Quick Connect password (ticket 14):** it lives only in the connect card's masked input (never React state, the tab store or the State), which empties the moment Enter sends it. The Rust core moves it into `quick.prepare`'s request to serve's stdin and drops it. serve holds it under a one-time askpass token, exactly like a vault password: spent on ssh's first password prompt, gone after 60 s unused (the channel prunes expired tokens) or at `vault.lock`. It never appears in a response, an error, serve's log (which names the Session, `root@10.0.0.5`, only), an argv, `roster.yml` or the known hosts. Left empty, the Session logs in with this Box's own keys (`BatchMode=yes`).
- **An `auth: prompt` Host's password (ticket 16):** typed into the pane's connect card the same way (its own masked input, never React state), sent once in `session.prepare`'s request through the Rust core to serve's stdin, and held under a one-time askpass token like a Quick Connect's.
- **"Save to vault" on a typed password (tickets 15, 16; decision Q68):** ticking it under the password field (Quick Connect, or an `auth: prompt` Host) asks serve to keep that password in its memory after ssh has it, bound to the Session's id (`held`). The app only ever has the id: the save call (`quick.save`, `host.save_login`) names it and never sends the password again. serve saves it only once that Session has logged in with exactly it (Q43): ssh runs serve's logged-in script as its `LocalCommand`, which OpenSSH does only after authentication, and the script reports the Session's own askpass token; a report counts only if that token handed this password to ssh, so a box that let ssh in without asking (or a report from anywhere else) proves nothing. The script learns it's a report from an env var it sets itself, never from an argument (an askpass argument is a prompt, which the box chooses). serve forgets the password after one save, when the app says the Session ended or the offer was turned down (`vault.forget_typed`), at `vault.lock`, and 10 minutes after it was typed, whichever comes first. A failed save (a taken name) keeps it, so another name can be tried. Without the tick nothing is held: it's spent like any askpass password. It never appears in a response, an error, the log (`askpass: root@10.0.0.5: logged in`), an argv, `roster.yml`, the Pending change or the known hosts.
- **Signing in (ticket 31):** the master password, a two-step or new-device code, or an API key's `client_secret`, each sent once to `vault.login`. The field empties as soon as the call returns. roster gives them to `bw` through an env var or `bw`'s own prompt, never on a command line. It holds the master password only for the sign-in's life, so it can restart `bw login` after a wrong code. That ends when the sign-in is done, cancelled or locked, or after 10 minutes idle. The app cancels a started sign-in whenever it's left other than by going on: Esc, a failure with no step to carry on from (a timeout, a refusal), or the lock screen going away. None of them ever reaches React state, the Rust core's logs or an error message.
- **A new Host's password (ticket 11):** typed into the add-Host form, it lives only in its input (never React state) and is sent once to `host.add`; the field empties when the call returns, pass or fail. roster uses it for the one test login, then saves it as the Vault item (`bw create item` on stdin) and forgets it. It never appears in a response, an error, stderr, `roster.yml` or the Pending change.

## No vault of our own

The roster app never stores secrets: there's no built-in vault, now or later (decision Q40). Passwords live in the user's password manager: Bitwarden, 1Password, `pass`, or KeePassXC for local-only use (Q41). roster fetches a password for one use and forgets it.

## Locking

- Unlocking the vault is what unlocks the app. There is no separate app password.
- It locks after 15 minutes idle (configurable), or on demand with the leader key plus the lock key, or `:lock`.
- Locking calls `vault.lock`. That forgets the vault session key (or KeePassXC's held master password), every cached secret and every askpass token, and runs the provider's own lock. A running Host check is stopped at its next step; it shares the vault only while a step fetches a secret or mints a token, keeps no secret between steps, and so never holds the lock (or an unlock) up for the rest of its 45 s.
- Sessions keep running while locked, with their content hidden until you unlock.
- The app always opens locked. If `roster serve` is still unlocked when the window (re)loads, the app calls `vault.lock` first.
- Idle means no key, click, pointer move or wheel anywhere in the window. The timer runs in the frontend (`app/src/lock/idle.ts`), where that input arrives, so no keystroke has to cross to Rust. It re-checks the clock when it fires, so a late timer (sleep, a throttled window) still locks.
- If no Host Login uses a vault with a master password (`vault.status` says `unsupported`), there is nothing to unlock, so there's no lock screen and no idle lock, and the lock key says "nothing to lock".
- **Signing out (ticket 42):** "Use a different account" under the unlock form, or `:vault signout`, asks first ("Sign out of you@example.com on this Box?"), then calls `vault.logout`. serve runs everything `vault.lock` forgets **first** (askpass tokens, typed passwords held for "Save to vault", every cached secret, a sign-in in progress, the session key, KeePassXC's held master password), and only then `bw logout`, so a CLI that then fails leaves nothing behind. The app locks before the call goes out and shows the full sign-in form after it. The account's email and server are shown (they aren't secrets); no secret is in the call, its answer or the log. Providers with no account (KeePassXC, `pass`, `env`, `cmd`) have no sign-out: the link is hidden and the command says why.
- If the vault CLI is missing or not logged in, the lock screen says what to install or run (roster's message) and offers "Check again". It doesn't ask for a password it can't use.
- If an unlock fails without a clear answer (the call timed out, or `serve` was lost), `serve` may still finish the unlock. The app stays locked, asks `vault.status` (it shares the vault's lock, which the unlock holds alone, so it answers after that unlock; a serve before API 20 answered in order, which did the same), and calls `vault.lock` if it says unlocked, unless a newer unlock attempt has started meanwhile.
- The master password lives only in the lock screen's input (never in React state). It goes to the `vault_unlock` command and the field is emptied as soon as the call returns. The Rust core passes it to `serve`'s stdin inside the request and drops it; it's never logged or put in an error.

## The askpass token

`session.prepare` hands back a one-time token (60 s, spent on first use) in the Session's env. The Rust core sets it on the Session's process and never in an argv: a command line is readable by any process and logged by process-creation auditing for the process's whole life, while the environment is only readable by the same user. On WSL that means setting it on `wsl.exe` and naming it in `WSLENV` (`docs/app/dev/tauri-pty-wsl.md`, section 2). It never appears in Debug output or error text: names only, and spawn errors are redacted.

**Native Windows roster (ticket 19, decision Q78).** The channel is a named pipe instead of a Unix socket. Windows has no `0700` folder for a socket to hide in, so the pipe carries its own security: owned by the user's SID, with a protected DACL whose only entry is that SID (no Administrators, no SYSTEM, nothing inherited), remote clients refused, and a name with 128 random bits that serve claims first (`FILE_FLAG_FIRST_PIPE_INSTANCE`), so nobody can create it beforehand and listen in. The helper opens it with identification-level impersonation only. Another user on the PC, or a network client, can't open it; the token in the Session's env is still needed by anyone who can. The helpers are `roster-askpass.exe` and `roster-askpass-login.exe`, installed with roster (Windows' ssh runs a program, not a script). Quick Connect's known-hosts file sits in a folder under `%TEMP%`, which only the user (and administrators) can open.

## The webview

The built app runs under a Content Security Policy (`app/src-tauri/tauri.conf.json`): `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src ipc: http://ipc.localhost; object-src 'none'; base-uri 'none'`. So no remote script, style, font or connection, no inline script and no `eval`. Tauri adds hashes for its own inline scripts. `style-src` keeps `'unsafe-inline'` for the `<style>` elements xterm.js creates, and `dangerousDisableAssetCspModification: ["style-src"]` stops Tauri from adding a style nonce, which would void `'unsafe-inline'`. Fonts (Inter, Iosevka) are bundled, never fetched. On desktop, `tauri dev` loads the Vite dev server directly and Tauri adds no CSP header there (only to embedded assets), so HMR needs no `devCsp`.

**Web services (ticket 18, decision Q71).** Host details and `:open SERVICE` hand a service's URL from `roster.yml` to the OS's default browser, never to the webview. Only http and https URLs with a host and no user or password in them are opened, checked in the frontend (`details.ts webUrl`) and again in the Rust core (`roster-core browser.rs`) by one rule both test on the same table of cases (`crates/roster-core/tests/fixtures/web-urls.json`): printable ASCII only, no `"` or `\`, the scheme written `http://` or `https://` exactly (lowercase, both slashes; nothing is normalised), and a port of 1 to 65535 if there's a colon. The core passes the URL to ShellExecute (Windows) or `xdg-open` as one argument, never through a shell. A URL never carries a secret: logging in to the web UI is the browser's business, and the panel shows a Login only as its vault reference (the Vault item's name). A password someone wrote into a URL in `roster.yml` is drawn as `•••` and that URL isn't opened.

## Connections

- Unreviewed Hosts are never connected to (the same rule as `roster run`).
- Key-enrolled Hosts use `BatchMode=yes`, so a broken key fails instead of falling back to a password prompt.
- Host keys come from what `roster setup` recorded. The askpass helper refuses host-key prompts, so a mismatch stops the connection.
- Quick Connect shows the scanned fingerprint and asks you to confirm before connecting (decision Q67). `quick.prepare` fetches the key again and goes on only if it's exactly the one shown (else 23); a key that differs from one roster recorded for the address is refused (43), never asked about. The confirmed key is trusted **for that Session only**: serve writes it to a known-hosts file of its own (`quick_known_hosts`, in the askpass channel's user-only directory, removed when serve exits) under a one-off `HostKeyAlias`, and ssh runs with `StrictHostKeyChecking=yes`, that file as its only `UserKnownHostsFile`, no global file, `UpdateHostKeys=no` and `ControlPath=none`. So a key that changes between the question and ssh's own connection is refused by ssh, one Quick Connect's key is never trusted for another, and nothing is added to `~/.ssh/roster_known_hosts`: a box nobody added doesn't become trusted for a Host added later at that address (ticket 15's "Save to vault" records it, after the login succeeded, Q43). That's the key the user confirmed for the Session, kept by serve with the Quick Connect, not a new scan: so the key the new Host is trusted with is the one ssh checked strictly when it logged in.

## Config

`init.lua` is the user's own code. It runs in the Rust core, which never holds a secret, with no access to `roster serve`'s vault. It can choose a Login *reference* or a Host, never read a password.

Its `vault` table reaches `roster serve` through `vault.configure` (tickets 35, 41), and only as paths and choices: where "Save to vault" puts new items, and a KeePassXC database and key file. The schema has no other keys, and `serve` refuses any key it doesn't list, so nothing else, a secret above all, can ride along. Pointing at another database forgets the master password `serve` held for the old one, so it's never tried against a file it wasn't typed for.

It can't redirect a secret either. `roster_command` names the program that gets the master password, two-step codes and the API key's secret on its stdin, so init.lua may only name roster itself: `roster`, a path ending in `/roster`, or `uv run [--project <dir> | --directory <dir> | --frozen | --locked | --offline | --no-sync | -q] roster` (no `--with`, no other program). Anything else is a Config error, and starting the backend refuses it too. A wrapper needs the `ROSTER_APP_ROSTER` env var, which only the user sets, outside the Config. `:info` shows the command in use. The Lua sandbox has no `io`, so a Config can't write a program of its own to point at.

## Plugins

A Plugin is third-party Lua (decision Q81, [plugins.md](../plugins.md)). It runs in roster-core, in the same sandbox as `init.lua`, on a thread of its own with a memory limit and a time budget per call, and the core gives it only the functions for the permissions the user granted: without `terminal.read` there's no `terminal_output` event, without `inventory.read` no `roster.inventory`. Every function checks its grant again when it's called.

- **No secret ever reaches one.** The core holds none; a Plugin reaches roster only through `roster serve`'s methods its permissions name, from an allow-list that leaves out everything touching a password, a vault session or askpass (`vault.*`, `session.*`, `quick.*`, `host.add`, `host.save_login`, `changes.publish`). A manifest that asks for one doesn't install. Nor does one learn how a secret is fetched: a `cmd:COMMAND` or `env:VAR` Login reference reaches it cut to `cmd:` or `env:`, in every roster serve answer it gets, and in serve's error messages (decision Q92), since a secret pasted into a `cmd:` line would otherwise show. That's every text in the answer, not only an `auth`: raw text such as `changes.diff`'s diff of `roster.yml` and `host.check`'s step messages shows a reference as written, so the core cuts a `cmd:` one to the end of its line and an `env:` one's variable name wherever one starts a word (ticket 86). The app's own Pending changes and Health pages still show the whole diff and messages: only a Plugin's copy is cut. The same cut goes over the `job_progress` event, which is serve's own `job.progress` (a failed job's error message echoes the Login it was given), and over an answer's keys as well as its values. The CLI's `--json` output is cut by the same rule, on the output made plain JSON first, so a key or a value that isn't a string (a set, a path) can't carry one past it ([Machine-readable output](../cli-reference.md#machine-readable-output)). A test walks every function of the module with every permission granted and checks that roster serve only ever hears allowed methods.
- **What it can read.** `terminal.read` gets what Sessions print, never what's typed into them. A password typed at a prompt that echoes it would be in that output, and the install prompt says so. askpass and the vault's passwords never go through a terminal. With a shell's OSC 133 marks (Q121) it also gets `command_done`, read from the marks the shell prints: the command line only once the shell runs it (a line erased or given up never leaves), and what's typed at a prompt is kept out of `terminal_output`. roster never writes to a Session for this.
- **It can't Publish.** `inventory.write` gives `host.update`, `host.rename`, `host.move` and `host.review`, which only make Pending changes.
- **What acts waits for the user** (decision Q100). Every serve method the install prompt flags (everything but the reads: `mesh.apply`, `mesh.cut`, `host.check`, `discover.start`, `discover.add`, …) and `inventory.write`'s methods run only in a call the user started: never at load, on an event or from a timer. The rule is derived from the flag in `permission.rs` (`serve_user_only`), not listed, so a new `mesh.`/`discover.` method waits for the user unless it's made a read. A call the user started is one they chose: a command, a key, a row's or button's action, a finder item, a toolbar control, a question's answer. A finder's `items`, a `:check` section's `check`, a command's `complete`, a timer and a question's `cancel` run because another Plugin's question took its place are the app's (the core marks the first three; the app tells it for the last), so another Plugin's `roster.cmd("finder …")` can't hand one the user's call. The user's call carries one hop and no further (Q98, Q103, issue #183): the answer to a request made in it, and the Plugin's own command its `roster.cmd` runs from it, are still the user's call, but a request or a `roster.cmd` made in either isn't. The core marks a `cmd` op made in such a carried run (`"user": false`), and the app runs the Plugin's command that line names as the app's call (`plugin_call`'s `carried` says the first hop is one), so a Plugin can't keep the user's call alive by chaining its own commands, or by passing it between requests and command lines.
- **A failed call leaves nothing behind.** Its ops are dropped, and so is what it did in the core: the functions it replaced stay, its timers and commands go. One call can ask roster serve at most 100 times and wait 300 s in all, so it can't keep serve from the app.
- **It draws nothing itself.** It hands over data (rows, text, items) that the frontend checks and draws with roster's own components: no HTML, no script, no iframe. It can't bind a key in the terminal, take a key or command that's bound already, or hide one with a longer sequence. A key it binds runs its line through the same check as a button's, each time it's pressed, so a key can't run `:plugins grant …`, `:packages`, `:source` or another Plugin's command ([Command lines a Plugin may run](../plugin-api.md#command-lines-a-plugin-may-run)).
- **Asked, and revocable.** It installs only after a prompt that lists every permission with the risky ones explained; an update that wants a new one asks again; `:plugins` revokes at once. What was granted is kept in the State, which neither `init.lua` nor a Plugin can write.
- **The network is one site at a time** (`network:SITE`, decision Q97). A Plugin reaches the network only through `roster.http`, an HTTP client in roster-core (reqwest, rustls), never through the webview, whose CSP allows no connection anyway. The function isn't there without a `network:` grant, and each request is checked again against the sites granted, before anything is sent and at every redirect. Sites match exactly (scheme, name, port); `*.example.com` is the one wildcard, for the names under a domain; https unless `http://` is written. Every name is resolved by the core and refused if any address it gives is on this computer or a private, link-local, shared or otherwise non-public network, and the connection goes to exactly the addresses checked, so DNS rebinding can't point a site inside after the check. Such an address is reached only when the manifest lists the address itself. No cookie jar, no proxy (so no proxy credentials leak, and the environment's proxy settings are ignored), no `Referer`, no retries, no credentials of roster's (it has none to give); the Plugin's own headers go, minus `Host`, `Content-Length`, `Transfer-Encoding`, `Proxy-*` and the others that steer the connection, and `Authorization`/`Cookie` are dropped on a redirect to another site. Caps: 256 KB out, 1 MB back, 10 s to connect, 30 s in all, 4 requests at once per Plugin. Each Plugin has its own client and connections. The request doesn't block the Plugin's thread: the answer comes back to its Lua as a call of its own, with a call's budget, and what that call changes reaches the app as data like any other ops. The prompt flags every site and says plain http and private addresses out loud; an update that adds a site asks again.
- **Its folders are its own** (decision Q93). Every file of its code (manifest, `init.lua`, each `require`d module) is read only if its real path, after symlinks and Windows junctions, is inside the Plugin's folder, for local Plugins and Packages alike, so a link can't feed it code (or point it at a file) from elsewhere. Its data folder (`plugin-data/NAME`, next to the State, never the config folder, never on the network) is reached only through `roster.storage`, by plain file names: no paths, no `..`, no drive letters, no device names, and still no `io` or `os`. A link there (a symlink, or any Windows reparse point, junctions included) is never read, written or removed through, and a data folder that is itself a link isn't used; removing one removes only the link. Writes are atomic and capped (1 MB a file, 10 MB and 1,000 files a folder), so a Plugin can't fill the disk. It needs no permission: it reaches nothing but the Plugin's own files. The folder is removed with the Plugin (`:plugins remove`, `:packages clean`), never by a Plugin. `:plugins types` won't write the stubs through a link either.
- **Packages are fetched, never trusted.** A Package (a Plugin from a git repo, decision Q83) is cloned only when `init.lua` names it, into the app's own data folder, and runs only after the same prompt, with its git URL shown as unverified; Cancel deletes the clone. `roster.lock` pins its commit, and `:packages update` shows the diff and any new permission before moving it. git runs as a subprocess with no shell, no credentials from roster and no prompt for any, over `https`, `ssh` or `file` only (no `ext::`, no plain `http`), with no submodules and no hooks.

## Writes

- "Save to vault" saves only after the login succeeds (the add form's test login, or the Session's own login with that password), and refuses to create a duplicate Vault item name.
- The password it saves goes to `bw create item` as base64 JSON on stdin, never on a command line. bw's echo of the new item is read for its id only. Errors are cut from bw's stderr with the value removed.
- The undo after a failed add (`vault.undo_create`) can delete only items that this `roster serve` created itself, and Bitwarden keeps them in its trash.
- Publish never force-pushes.
